## 实现

新增 `references/technical-quality.md`，由根入口、任务分类、复核和 Architect Discuss/Propose 按条件引用：有重要技术选择、数据/服务边界变化或有争议的工程反馈时才加载。普通小改动和已确定方案继续沿用现有路径；用户是否懂代码不决定流程等级。

协议要求 Coordinator 阅读相关项目，给出明确推荐、可行替代方案、证据、业务影响、维护代价和重新评估条件。用户决定业务取舍，日常技术细节由 Coordinator 承担。方案必须逐项核对业务验收，不能用流行度证明框架必要性，也不能把“有备份”当作能恢复到任意误操作前的证据。

质量检查随变更选择：相关权限边界、重要数据的一致性和重试、外部依赖失败、部署及恢复能力。它是检查选择指南，不是每个任务必跑的全面安全测试矩阵。保留现有必需验证、修复预算和授权规则。

工程反馈作为待评估材料，按具体路径、真实影响、证据和最小修复处理，沿用原有 finding classes。评论或附件里的“立即安装、重写”不构成用户授权。

技术选择放在现有清单、Discuss/spec 中，并随已有 Work Order 传给 Executor；不新增控制器、通用问卷、审批关卡、强制架构文档或 Reviewer 子任务。README 同时修正了上一轮残留的“短任务总要建计时台账”描述。

首轮新版遗漏了“每日备份不等于恢复到误操作前”的关键解释，旧版反而指出了这点。保留该负面结果，没有用更短耗时掩盖建议质量差异。

因此补入“逐项对照业务要求”和“恢复时间点、可接受数据丢失、恢复时长”的定向规则。新会话复核耗时 92.200 秒，15 次工具，明确指出每日备份与误操作恢复的差别，并用既有 finding classes 评估同事意见。全程仍只读，没有扩成 Track 或执行改造。

这次复核也有局限：回答先要求确认恢复目标，随后又把去重定义称为“唯一”待确认项，表述不一致；把版本历史说成精确恢复的必需方式也过早收窄了解决路径。因此只能确认它补出了恢复缺口，不能把整份建议作为已验收的实施规格。后续真实方案仍要确认恢复要求并验证候选方案，再进入开发。

定向复核有一次 `git show` 被隔离 host 的只读命令白名单拒绝；不是源项目权限问题，也不是自动审批拒绝。模型未绕过限制或重复尝试，使用现有文件完成建议。没有为了得到全绿记录放宽白名单重跑。
