## 改动

- 普通的 implement/fix/add/continue 不再单凭动词触发 Architect；显式生命周期意图或已识别 Track 才进入该路由。Status、Review 的只读约束保留。
- 根 Skill 保留完成条件、15/45 分钟检查点入口及原有修复预算；重复检查、复核范围扩张或检查点才加载详细收敛协议。普通短任务不额外建台账或报告耗时。
- 详细协议扩展已有清单，避免重新整理一套账本。没有减少必要验证或安全、权限、数据完整性要求。
- 增加可选 `review-closure` 练习：实现已完成，准备阶段真实运行测试并记录哈希；模型须评估额外边界测试建议是否属于原验收范围。默认三场景评测保持不变。

## 解释与边界

保留本轮入口澄清和按需加载，因为它们减少固定文本与不必要的账本要求；不把这次结果标记为交付速度验收通过，也不继续反复跑小样本直到得到好看的数字。

本次覆盖了复核建议带来的范围扩张压力，未覆盖真正持续 15/45 分钟、多轮修复耗尽或 Track 阶段验收。新版复核未读取 `references/delivery.md`，因此不能把良好收尾归因于新详细协议的执行。后续应在真实长需求中观察首次实现之后的检查、待办、复核和等待耗时，确定是否需要进一步限制短任务的计划工具调用。

每场景每版本仅一次，没有估计供应商响应波动。最终文件检查显式排除了 OpenCode 自动生成的 `.opencode/node_modules`、`package.json`、`package-lock.json`、`bun.lock`、`.gitignore`；原始评估器遇到这些依赖符号链接会拒绝，因此本次使用保留原始目录的独立探针与哈希汇总，不能称为原始 assess CLI 验收通过或完整安全等价证明。模型没有发起安装依赖的工具调用。
